# Neutral conformance suite format

The suite is a directory of cases that any implementation of the Bennett ISA
command-line contract can be judged against: the reference interpreter, the
future VM and the plugin run the same files, as WebAssembly's spec tests and
test262 do for theirs. Nothing in a case refers to an implementation's test
harness, language or build. The runner (`suite/run.py`, stdlib only) needs
only an executable that speaks the contract.

## Layout

```
suite/
  FORMAT.md            this file
  run.py               the runner
  tools/import_fixtures.py   seeds cases from the reference interpreter's fixtures
  tests/               unit tests for the runner (fake binary) and the real-case gate
  cases/<name>/
    object.bisa        the object under test, byte-exact (LF endings preserved)
    expect.json        the expectations (below)
    notes.md           the original hand derivations (the fixture's .comments), byte-exact
    <other files>      inputs a run references as $CASE/<file> (for example replies JSON)
```

## expect.json

| key | meaning |
| --- | --- |
| `spec` | specification version judged, `isa-0.8` |
| `source` | where the expectations came from: `reference-interpreter@<commit>` |
| `clauses` | non-empty list of section tags, `ISA-4.5` style, the case exercises. Seeded from the `.comments` citations and the Rust tests; the clause-graph tool refines them to paragraph IDs later. `run.py --tags-json` emits `{case: [clauses]}` for its coverage tool |
| `hashes` | `{object, symbols: {name: {interface, closure}}}` as printed by `hash` (`closure` is null when the closure has an unpinned import). Compared to the implementation's `hash` output; the symbol sets must be equal |
| `check` | `"ok"`: `check` exits 0 with `status` `"ok"` (and the same identities as `hashes`). Or `{exit, stderr_contains}`: `check` exits with that nonzero code and stderr contains the substring |
| `runs` | list of run records |

At least one of `hashes`, `check`, `runs` must be present and non-empty.
A case with none is a failure of the suite, never a skip.

### Run record

```json
{"cmd": ["run-oracle", "$OBJECT", "inc8", "--input", "255", "--budget", "3"],
 "stdout_json": {"code": 0, "payload": 0, "steps": 3},
 "exit": 0}
```

* `cmd`: the subcommand and its arguments (the implementation binary is
  argv[0]). Each argument has `$OBJECT` replaced by the absolute path of the
  case's `object.bisa` and `$CASE` by the absolute path of the case
  directory. The process runs with the case directory as cwd, with `DISPLAY`,
  `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS` and `BROWSER` removed from its
  environment. Timeout: 300 s.
* `exit`: required exit status.
* exactly one of
  * `stdout_json`: stdout is parsed as JSON and compared structurally
    (key order and whitespace irrelevant; `true` is not `1`; numbers compare by
    value; `NaN`/`Infinity` are rejected). Integers above 2^53 - 1 are decimal
    strings by the contract (ISA 9.1), so no precision is lost.
  * `stdout`: stdout compared byte-exactly (used for diagnostics, where it is `""`).
* `stderr_contains`: a string or list of strings that stderr must contain.
  Mandatory when `exit` is nonzero, so a diagnostic is pinned to its cited rule.

Any difference, a missing field, an unknown key, an unparsable file or a case
without expectations fails the case. The runner prints
`case | hashes | check | runs | result`, then one line per problem, then
`checked N/M cases`, and exits 0 only when N = M. `-` in a column means the
case makes no expectation of that kind.

## Running

```sh
env -u DISPLAY -u WAYLAND_DISPLAY -u DBUS_SESSION_BUS_ADDRESS -u BROWSER \
    TMPDIR=$PWD/.tmp \
    python3 -I suite/run.py --binary <path-to-implementation> [--cases suite/cases]
python3 -I suite/run.py --tags-json            # clause tags only; runs nothing
```

`--binary` defaults to `$BENNETT_ISA_BINARY`. Tests:

```sh
BENNETT_ISA_BINARY=<path> python3 -I -m unittest discover -s suite/tests
```

`test_real_cases.py` fails (it does not skip) when `BENNETT_ISA_BINARY` is
unset.

## Provenance and regeneration

Expectations are generated by running a real binary, never typed by hand.
`tools/import_fixtures.py --binary B --fixtures F --source-repo R` copies each
fixture and `.comments`, runs `hash` and `check`, runs the planned commands,
and writes what the binary printed. The commands come from how the reference
interpreter's Rust tests (`tests/cli.rs`, `cli_xam.rs`, `oracle.rs`,
`step_machine.rs`, `wide_oracle.rs`, `quantum*.rs`, `classical.rs`, ...) drive
each fixture, widened with the hand derivations in the `.comments`. Those
hand-derived values are assertions: the import aborts if the binary disagrees
with one, instead of recording the disagreement as truth. Hashes the Rust
tests pin independently (hashlib) for `mutual`, `classical` and the `r9-*`
fixtures are asserted the same way. The import refuses to run when
`reference-interpreter/` of the source checkout has uncommitted changes, so
`source` names the commit the binary was built from. Regeneration is
deterministic (byte-identical output).

Outputs of the reference CLI beyond what the ISA fixes (the `trace` records of
`run-cc`, `memory_digest`, tape and budget reporting) are recorded in full; a
competing implementation that reports a different but valid shape will fail
those runs, which is the signal to either align the contract or relax the run.
That decision belongs to the clause-graph and spec owners, not to the runner.

## Seed corpus: 16 cases

`actions arithmetic classical control_flow heap inc8 mutual nested
r9-codex-oracle r9-loop r9-sol-oracle r9-sol-qinplace registers sum_db
tiny_memory wide`. All 16 have hashes, check and runs.

### Partial imports

No fixture was reduced to hash/check only. Every one has CLI runs. Parts of the
Rust tests that use library-only APIs, or cost too much through the CLI, are
not in the suite:

* `arithmetic`: the ignored full 8-bit division sweep (65536 x 4 runs) and the
  per-prefix `step-check` sweep over all functions (library `compare`).
* `heap`, `wide`, `tiny_memory`, `inc8`: per-prefix forward/inverse stepping and
  `commit` of every target and fault value use `OracleMachine` /
  `OracleVectorMachine` directly. The CLI covers them through `step-check`
  (exhaustive `tiny`, `inc8`, `heap`, `fault_small257`) only.
* `wide`: the `u128` adapter limit test (`add257` through `OracleMachine`).
* `classical`, `registers`: the machine-level `snapshot` equality and
  `request`/`reply` stepping (`ClassicalMachine::reply`) are covered by the
  CLI's `reverse` (`equals_entry`) and `--replies` runs; the registers static
  error tests and r3/r4 dynamic-alias tests build objects in memory with
  `support::object` and are not fixtures.
* `control_flow`: the `QuantumState::exact_support` assertions and the r11
  `probe` objects (separate pinned texts, not fixtures) are not imported; the
  fixture's own actions are run through `run-action`.
* `nested` / `inc8` rejecting out-of-range literals mutate the fixture text in
  memory and so are not fixture cases.
